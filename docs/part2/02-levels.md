# Part 2 — levels

This proposal treats Part 2 as a content extension of the current game: six new playable
levels follow Part 1's six worlds, then the existing non-playable finale remains the closing
scene. The level files stay pure data and continue to use `composeMap()`, `laneFor()`,
`airFor()`, `arcCollectibles()`, and the generic `buildLevel()` path.

The new chapters are numbered 7–12 so a completed Part 1 run can continue naturally. All
new user-facing names and any custom hints are keys in `src/i18n/it.js`, `en.js`, and `ru.js`;
level data carries keys, never prose.

### Curve rules

- Level 7 deliberately starts below Part 1's castle difficulty. It teaches the sequel's
  visual language without adding a new control rule.
- Levels 8–10 add one timing problem at a time, then combine it with an already-known
  enemy. A checkpoint always banks the preceding set-piece; it is not placed on a hazard,
  at a ravine lip, or on a forced spring bounce.
- Levels 11–12 are hard because of sequencing and timing, not because global enemy speeds
  change. Keep enemy tuning in the level data and `def.feel`, as in Part 1.
- Critical-path gaps remain `w <= 2`; there is no double jump. Any `M` used by the route
  launches onto a semisolid `#`, never onto a solid `=` slab. `+` and all high routes remain
  optional; the player must be able to finish with run, jump, and wait alone.
- Place no heart directly before a death loop. Each `H` is one per level at most, sits clear
  of hazards, and is remembered through `heartsTaken` so a checkpoint retry cannot create
  infinite lives. Part 2 grants three hearts total, on 9, 11, and 12, preserving the scarcity
  established by Part 1 while supporting the final difficulty spike.

## Existing tile vocabulary

The sketches use the current `build.js` legend. A blank cell is air; the two bottom rows are
normally generated by `composeMap()` and show as `=` here. The sketches are beat sketches,
not complete 116–140-cell maps, and are not to scale.

| Token | Meaning |
| --- | --- |
| `=` | Solid ground or terrace |
| `#` | One-way semisolid platform |
| `^` | Static hazard |
| `o` | Themed collectible |
| `H` | Arcade heart, `+1` life |
| `F` | Checkpoint |
| `M` | Spring |
| `!` | Crumble platform |
| `c`, `h` | Crab, hopper |
| `f`, `g`, `S` | Flyer, swooper, armored swooper |
| `r`, `s` | Roller, falling stalactite |
| `w`, `B`, `P` | Updraft, breeze, pendulum |
| `+`, `*` | Feather, star power-up |
| `@`, `>` | Spawn, goal portal |
| `G` | Existing multi-phase boss anchor |

Moving platforms are deliberately not ASCII tokens. They remain `movers` entries with cell
coordinates, travel amplitude, period, and optional phase, so the existing wait-at-the-edge
behavior and native rider physics are reused.

**New tile tokens: none in this baseline proposal.** This keeps the first Part 2 pass inside
the existing renderer and collision vocabulary. If a future mechanic needs a new token, add it
to `build.js`'s legend and its explicit switch case before using it in a map; unknown
characters currently become empty air.

## Key-beat layout sketches

Every sketch uses `y=11` for the normal lane and `y=12–13` for generated ground. A blank in
the ground rows is a ravine. The exact coordinates in the level table are authoritative when
the maps are authored.

### Level 7 — spring-to-moonleaf route

The spring is directly below the one-way landing strip. The optional upper route pays out
`o`; the lane route continues without it.

```text
y=7                   ###  ###
y=10                         o
y=11  @  h  ^     M     c        F      >
y=12  ==========  ================  ========
y=13  ==========  ================  ========
```

### Level 8 — reflected canyon transfer

The `movers` entry fills the two-cell ravine when it reaches its far extreme. The `!` route

### Level 9 — cloud lift and guarded landing

The `w` column carries the heroine through the vertical beat. The spring lands on `#`; the
`S` is offset from the required landing line so it cannot deadlock the jump.

### Level 10 — bell-marsh crumble crossing

The `B` columns soften a short crossing; the crumble strip gives a visible countdown before
the safe lower route resumes. `g` and `S` are separated so their dive windows remain readable.

### Level 11 — forge timing gauntlet

The pendulum bobs and falling stalactites are staggered. The `H` is after the second flag,
before the final timing sequence, with several clean cells on both sides.

```text
y=6              s                 s
y=8                              P
y=10                                      H
y=11  @  ^  r    F       P    s      F       r      >
y=12  ==========  ==  =================  ==  ========
y=13  ==========  ==  =================  ==  ========
```

### Level 12 — flat arena and logical boss gate

The final approach ends on a wide, flat staircase top. The boss is an existing `G` anchor,
not an ordinary `enemy`; only its spawned hazards damage the heroine. After three reliable
stomps, its key lands on the same floor and `>` remains logically sealed until the key is
collected.

```text
y=4                                            G
y=7                                                 o
y=10                                      H
y=11  @  ^      F       S    g      F                >
y=12  ==========  ==  ================================
y=13  ==========  ==  ================================
```

The `G` in the sketch is the single boss anchor. Keep the arena wide enough for left/right
dodging and put the goal beyond the logical gate, never behind a physical wall.

### Part 2 boss acceptance criteria

Reuse the Part 1 `G`/`makeBoss()` contract unless the boss design is intentionally expanded:

- tag the body as `boss`, not `enemy`, so contact with the body cannot create an accidental
  side-collision softlock;
- detect stomps during overlap (`onCollideUpdate` behavior), not only on collision entry;
- keep a fixed, recurring vulnerable window below the single-jump apex, with no shrinking
  window on later hits;
- keep every shockwave jumpable and every falling hazard telegraphed;
- drop the key on the flat arena floor at a reachable position;
- gate `>` logically on boss defeat plus key pickup, with no physical door that can trap her;
- keep the checkpoint before the final approach so a failed attempt is retriable without
  replaying the whole level.

## Registration and progression changes

Implementation is intentionally the same registry path as Part 1:

1. Add `src/levels/level7.js` through `src/levels/level12.js`. Each exports `LEVEL_7` …
   `LEVEL_12`, imports only the mapkit helpers it needs, sets `id`, `nameKey`, `tileSize`,
   `theme`, optional `feel`/`movers`/`decor`, and a `composeMap()` result.
2. Import those six definitions in `src/levels/index.js` and add numeric entries `7` … `12`
   to `LEVELS`. Do not add a scene per level; `game.js` already asks the registry for the
   current definition and calls `buildLevel()`.
3. Change the single source of truth in `src/config.js` from `MAX_LEVEL = 7` to
   `MAX_LEVEL = 13`. As today, `1..12` are playable and `13` is the finale sentinel. The
   existing `level >= MAX_LEVEL - 1` last-level effects then correctly apply to level 12;
   `hasLevel(13)` stays false, so the reward button continues to `finale`.
4. Extend `SKINS` with six Part 2 reward entries whose `afterLevel` values are `7` … `12`
   (proposed keys: `veil`, `brooch`, `boots`, `sleeves`, `hairpin`, `ballgown`). The existing
   `unlockedSkinKeys()` and `skinUnlockedBy()` logic will then carry the wardrobe forward;
   each sprite is generated by the asset pipeline, not hand-edited.
5. Add `level.7.name` … `level.12.name`, the six skin labels, any boss/goal hints, and any
   finale copy to all three dictionaries. Italian copy must remain feminine and personal to
   Anna (`Bentornata`, `Sei pronta`, `Sii la prima`), with no literal strings in level data.
6. Add generated backgrounds, theme props, collectible art, and optional music under stable
   `config.js` asset keys. `npm run gen` remains the source of generated art; the Yandex archive
   remains static and does not need a server or new API.

`state.js` already clamps `currentLevel` through `MAX_LEVEL`, and the existing cloud-save
merge takes the furthest unlocked level. No second progression counter should be introduced.
The finale, leaderboard time, Coccoline receipt, and Yandex submission remain after level 12,
not after an extra playable level.

## Open questions

- Is Part 2 shipped as the same save-compatible game or as a separate sequel package? If it
  is the same package, an old `pj.currentLevel === 7` means “Part 1 complete” today but means
  “start Part 2 level 7” after the change. We need an explicit decision about preserving the
  old `Rivedi il Gran Ballo` access, likely with a separate completion flag rather than
  overloading `currentLevel`.
- Should the six proposed wardrobe layers ship with Part 2, or should the existing six-layer
  outfit remain the complete gift? The level/reward flow supports either, but new layers need
  generated sprites and all three i18n labels.
- Is the Part 2 boss a new visual/Italian identity using the proven `G` implementation, or a
  genuinely new phase machine? Reuse is the safe baseline; a new phase machine needs a separate
  boss acceptance test before it can gate the final portal.
- Do the 132–140-cell maps and denser particle themes hold the mobile/Yandex frame budget? The
  answer should come from `npm run test:mobile` and a real-device pass after implementation;
  shorten Level 12 before weakening the culling and collider-meshing invariants.
